# 08 标的代码化与交易员决策系统

> 状态：设计草案，待确认后实施
> 目标：把 docs 里每一篇标的文档「代码化」——标的、状态、持仓、纳入/退出条件全部落库为结构化数据，由交易员决策系统每日评估、产生交易决策信号。

---

## 一、背景与目标

### 现状痛点

- `docs/A股研究/公司研究/` 积累了 200+ 篇标的文档，十节模板结构成熟，但所有信息（状态 🟢🟡⚪、持仓、成本、纳入条件、心理锚）都锁在 markdown 表格的自然语言里，代码无法读取。
- 研究结论与交易执行脱节：文档里写了「长江电力 PE <18x 或股息率 >4% 纳入」，但没有系统每天检查这个条件是否触发。
- RAG / LLM 投研 Agent 规划已久（`docs/AI投研/`），但缺少结构化数据底座，检索只能全文模糊匹配。

### 核心目标（已与用户确认）

1. **每一个标的代码化**：标的元数据、状态机、持仓记录、纳入/退出条件、关键假设、跟踪指标全部结构化落库。
2. **形成交易员决策系统**：每日拉取行情估值快照 → 评估每个标的的条件 → 生成决策（买入/卖出/加仓/减仓/观望 + 理由）→ 输出信号。
3. **权威来源在数据库**：SQLite 是唯一权威数据源，markdown 文档降级为展示层（由 DB 渲染或人工维护）。

### 明确不做（本阶段）

- 不改造 `docs/AI投研` 的 RAG/LLM 方案（留待后续在结构化底座上实施）
- 不自动下单：决策系统只产出信号/建议，执行仍走人工或现有 live 引擎
- 不一次迁移全部 900+ 文档：先试点「公司研究」分类

## 二、总体架构

```
docs/A股研究/公司研究/*.md        ← 展示层（人读，迁移后由 DB 渲染）
        │  一次性迁移（试点）
        ▼
data/desk/desk.db（SQLite）      ← 权威数据层（唯一事实来源）
        ▲
        │ 读写
app/desk/（新模块）               ← 决策层
  ├─ repository.py  标的/条件/持仓 CRUD
  ├─ conditions.py  条件 DSL 解析与评估
  ├─ snapshot.py    行情估值快照（PE/PB/股息率，xtdata/baostock）
  ├─ engine.py      每日决策流水线
  ├─ report.py      决策报告（rich/markdown）
  └─ docsync.py     文档渲染 + 迁移导入
        │
        ▼ 决策输出
data/desk/decisions/YYYYMMDD.json   ← 决策信号文件
        │
        ├──▶ 人工确认 → QMT 手动下单（当前）
        └──▶ app/production/ 兼容格式 → pos_file.json（后续对接）
```

### 分层职责

| 层 | 位置 | 职责 |
|------|------|------|
| 展示层 | `docs/` | 人读文档；迁移后由 DB 渲染生成，不再手工维护表格 |
| 数据层 | `data/desk/desk.db` | 标的/条件/持仓/决策的唯一事实来源 |
| 决策层 | `app/desk/` | 条件评估、决策生成、报告输出 |
| 执行层 | 现有引擎 | `app/engine/live`、`app/production`（本次不改造） |

## 三、数据库设计（SQLite）

沿用 `app/engine/live/ledger.py` 的 stdlib sqlite3 风格。**所有价格/金额字段用 TEXT 存 Decimal 字符串**，时间戳用 ISO8601 字符串。建表语句统一放 `app/desk/schema.py`，带 `DESK_SCHEMA_VERSION` 版本号。

### 3.1 securities — 标的注册表（核心表）

| 字段 | 类型 | 说明 |
|------|------|------|
| symbol | TEXT PK | 代码，如 `600900.SH` |
| name | TEXT | 名称 |
| industry_l1 / l2 | TEXT | 申万一级/二级 |
| market | TEXT | SH/SZ/BJ |
| listed_date | TEXT | 上市日期（未上市为 NULL） |
| status | TEXT | 研究状态：`green/yellow/white/blue/watch/learn`（对应 🟢🟡⚪🔵🔭📚） |
| rhythm | TEXT | 投资节奏：`config/research/preipo/closed/learn`（配置型/研究型/前瞻型/已平仓/学习型） |
| layer | TEXT | 岁寒策略分层：`pine/bamboo/plum`（松/竹/梅），无则 NULL |
| target_weight_min / max | TEXT | 目标仓位区间（Decimal，如 `0.05`/`0.15`） |
| core_thesis | TEXT | 核心逻辑一句话 |
| doc_path | TEXT | 对应主文档相对路径 |
| updated_at | TEXT | 更新时间 |

状态机（与文档「状态切换规则」一致）：

```
blue(IPO前) → yellow(研究型) → green(配置型) → white(已平仓)
learn(学习型) → yellow(研究型) → ...
```

### 3.2 positions — 持仓记录

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增 |
| symbol | TEXT FK | 标的 |
| shares | INTEGER | 股数 |
| avg_cost | TEXT | 成本均价（Decimal） |

| closed_at | TEXT | 清仓日期（NULL=在持） |
| realized_pnl | TEXT | 已实现盈亏（Decimal，清仓后回填） |
| note | TEXT | 备注（岁寒层、建仓理由） |

### 3.3 conditions — 纳入/退出条件（决策核心）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增 |

| rationale | TEXT | 理由（来自文档「决策结论」表） |
| active | INTEGER | 是否启用（1/0） |

### 3.4 metrics — 行业关键跟踪指标

| id | INTEGER PK | 自增 |
| symbol | TEXT FK | 标的 |
| name | TEXT | 指标名（如来水量、股息率） |
| current_value | TEXT | 当前值（Decimal 或文本） |
| trend | TEXT | 趋势：up/down/flat |

| source | TEXT | 验证来源 |
| frequency | TEXT | 跟踪频率 |
| updated_at | TEXT | 更新时间 |

### 3.5 assumptions — 关键假设

| 字段 | 类型 | 说明 |

| id | INTEGER PK | 自增 |

## 四、条件 DSL

条件以 JSON 存于 `conditions.logic`，支持 `any_of` / `all_of` 组合，叶子节点为 `metric + op + value`：

```json
{
  "any_of": [
    {"metric": "pe_ttm", "op": "<", "value": 18},
    {"metric": "dividend_yield", "op": ">", "value": 4}
  ]
}
```

对应文档原文：长江电力「纳入条件：PE <18x 或股息率 >4%」。

支持的 metric（首期）：`price`、`pe_ttm`、`pb`、`dividend_yield`（均来自 snapshot 表）；后续可扩展 `bond_yield_10y`（十年国债，需额外数据源）。
支持的 op：`>` `<` `>=` `<=` `==` `!=`。

`conditions.py` 提供：
- `parse(logic_json) -> Condition`：解析为可评估对象
- `evaluate(condition, snapshot) -> TriggerResult`：返回是否命中 + 命中路径 + 实际值
- 非法 metric/op 在解析时报错（fail-fast），不静默跳过

## 五、每日决策流水线（engine.py）

```
1. 加载标的清单       repository.list_active_securities()（排除已平仓/学习型）
2. 获取行情快照       snapshot.fetch(today, symbols)（xtdata 优先，baostock 兜底）
3. 评估条件           逐标的评估 entry/exit 条件 → TriggerResult 列表
4. 生成决策           规则：
                       - exit 命中且持仓 >0        → sell（卖出）
                       - entry 命中且无持仓         → buy（买入）
                       - entry 命中且有持仓且未满仓 → add（加仓）
                       - exit 命中且无持仓         → watch（警示）
                       - 无命中                    → hold（持有/观望）
5. 持久化 + 输出       decisions 表 INSERT；data/desk/decisions/YYYYMMDD.json
6. 报告               report.py 渲染 rich 表格 + markdown 日报
```

决策 JSON 输出格式（与 `pos_file.json` 理念一致，字段超集，后续可适配）：

```json
[
  {
    "date": "2026-08-07",
    "symbol": "600900.SH",
    "action": "buy",
    "triggered": [{"metric": "pe_ttm", "op": "<", "value": 18, "actual": 16.8}],
    "reason": "PE(TTM) 16.8 < 18，触发纳入条件",
    "status": "proposed"
  }
]
```

## 六、文档同步策略

### 6.1 迁移导入（一次性，试点）

`scripts/migrate_company_docs.py` 解析公司研究文档 → 写入 DB：

1. 解析主文档头部的「当前跟踪状态」行 → status/rhythm/layer
2. 解析「一、公司概览」表 → 行业/上市时间/市值
3. 解析「十、决策结论」中的「触发买入/卖出条件」表 → conditions（人工校对 DSL 语义）
4. 解析「九、操作日志」表 → operations
5. 解析「五、行业关键跟踪指标」表 → metrics
6. 解析「三、核心投资逻辑」关键假设 → assumptions
7. 无法可靠解析的行 → 跳过并输出 `migration_report.json` 供人工补录

试点范围（3 只，覆盖不同状态）：长江电力（🟡 观察，有条件未触发）、京东方 A（🟢 持仓）、TCL 科技（🟢 持仓）。

### 6.2 文档渲染（DB → docs）

迁移完成后，`docsync.render_doc(symbol)` 用 DB 数据重写主文档的表格区（持仓概览、跟踪清单、操作日志），保留分析文字区。渲染只覆盖模板化章节，不动自由文本章节（商业模式、决策结论的分析段落）。

### 6.3 一致性原则

- DB 是权威：修改状态/持仓/条件一律走 `app/desk` API 或迁移脚本，不直接改文档表格
- 文档自由文本可继续手写，与 DB 表格互不覆盖
- 提供 `scripts/check_docsync.py` 校验文档表格与 DB 是否漂移

## 九、风险与开放问题

| 风险/问题 | 影响 | 对策 |
|------|------|------|
| 文档表格格式不统一（表格列错位、emoji 状态混用） | 迁移解析失败率高 | 试点 3 只先验证；解析失败行进 migration_report 人工补录；后续文档由 DB 渲染，格式从源头统一 |
| 条件语义复杂（「十年国债 <1.3%」需要行情外数据） | 部分条件无法自动评估 | 首期只支持 snapshot 内 metric；无法评估的条件标 `active=0` 并记录原因，不进决策 |
| 快照数据源不稳定（xtdata 需要行情终端在线） | 每日决策跑不了 | snapshot 多源兜底（xtdata → baostock → 本地缓存），失败时决策输出明确标注「快照缺失」 |
| 决策直接对接交易有误操作风险 | 资金损失 | 本期决策只输出信号文件，执行保持人工确认；对接 production 留到阶段 5 并加风控复核 |
| DB 与文档漂移 | 两处数据打架 | DB 权威 + `check_docsync` 校验脚本 + 文档渲染回写 |
